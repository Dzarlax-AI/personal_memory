Periodic project-catalog maintenance

Revision 1 · Approved · Local implementation accepted · 2026-10-13

1. Goal and bounded scope

Provide optional server-side maintenance of registered project descriptions using a generative model selected by the operator. Registration remains automatic through ensure_project; users do not manually maintain a catalog. Maintenance, write classification and read ranking remain independent. Maintenance is disabled by default. This stage adds a catalog-only execution path: it uses registered declarations and bounded client-read README/AGENTS evidence, without scanning historical facts or changing fact tags.

The model proposes concise summaries, aliases, owned components, ownership boundaries, supported dependencies and examples for existing projects. Default publication remains review. The existing explicit evidence_bounded policy may publish validated descriptive updates; identity, namespace, owner, project key, tag and name remain immutable. Structural evidence validation does not prove factual correctness, so automatic publication requires separate model-quality acceptance.

Acceptance: disabled mode causes no maintenance provider calls or credential reads; catalog-only mode causes zero Qdrant requests; every eligible card with usable evidence receives its turn; unchanged inputs survive restart without repeated inference; concurrent registration prevents stale publication; both local and hosted configurable models satisfy the same validated result contract.

3. Proposed configuration and compatibility contract

  • Add maintenance.scope with catalog_only and facts_and_catalog. Omission preserves the existing facts_and_catalog behavior for compatibility. New recommended examples explicitly select catalog_only. enabled=false remains the universal default and initializes no maintenance worker.
  • Add max_projects_per_run, proposed default 4 and valid range 1–32. It is an upper bound; serialized request and evidence limits can reduce a batch. Existing max_facts_per_run retains its meaning only in the legacy facts_and_catalog path.
  • The operator selects maintenance.profile, and the profile's model and endpoint. No default Luna, hardcoded model family, silent fallback or substitution. A local HTTP endpoint requires local=true. Hosted profiles require their configured private key file. Existing response_models validation remains exact.
  • Reuse interval_seconds and shared daily call/token accounting. A suggested operator interval is six hours, limiting a single worker to at most four scheduled dispatch opportunities per day before deduplication; it is an example, not a forced schedule. One provider dispatch per tick, no HTTP retry, no startup inference or catch-up burst.
  • Write/read modes and profiles are untouched. allow_ai_processing on a fact is never reused as maintenance consent. Maintenance egress must separately admit the selected catalog descriptions and original evidence.
  • Configuration changes require the existing service restart; no hot-reload or new MCP administration contract is introduced. Disabled installations need neither a maintenance model nor maintenance credentials.

This is an additive configuration and persistent-worker-state amendment to the already implemented optional layer. Local implementation approval covers its compatibility checks; production enablement and private source transmission remain separate actions.

4. Catalog-only processing and publication

  1. Load one validated immutable catalog and filter eligible cards by existing operator egress policy. Missing/empty catalog, denied cards or cards without original evidence produce a finite skipped outcome. Preserve the baseline memory service.
  2. Select cards fairly using a persisted stable namespace/tag cursor and per-card processed fingerprints. Include the full original declaration and client evidence for each selected card, subject to existing per-card limits. Do not use generated descriptions as new original evidence.
  3. Pack complete cards within 32 excerpts, 16 KiB source evidence and 128 KiB final serialized request. Leave unselected cards unchanged. A card that cannot fit alone is skipped with a reason; it must not starve other cards. Keep catalog-only input Facts empty and require an empty grouping proposal.
  4. Request descriptive proposals for selected cards, using their supplied aliases and sources. Preserve the existing identity and provenance constraints. Existing nonselected cards may provide bounded ownership context, but cannot be changed or cited as original evidence for another project.
  5. Persist the private proposal and processing receipt before advancing progress. Bind each receipt to exact original sources, selected model/profile, publication policy and relevant comparison context. Model or relevant source/boundary changes allow a new run; a worker's own descriptive publication must not create an inference loop. Preserve compatible legacy fact-sweep state in a separate state branch.
  6. For review, retain the proposal without changing the active catalog. For explicitly configured evidence_bounded publication, adapt the existing merge checks to the selected subset: re-read the exact base hash, check selected dependencies and retain all unselected entries unchanged. Concurrent registration, cancellation, malformed output or uncertain evidence prevents publication.
  7. On publication, write classification and future optional read ranking use the new immutable catalog through their existing loaders. Older write recommendations may correctly return outdated/catalog_changed. No fact is rewritten, retagged, deleted, moved between namespaces or merged.
  8. Expose content-free operational status through a new CLI status subcommand: configured scope/model, last dispatch/outcome, queued/completed/skipped counts and finite failure reason. No fact texts, evidence excerpts, private identifiers, keys, raw responses or endpoints in status output.

Missing evidence remains missing. A clean installation can register its first project without a model, then produce a catalog proposal when the independently enabled worker has admitted sources. The worker has no filesystem discovery, repository crawling, mutation tools or permission to invent projects.

6. Planned checks and acceptance evidence

No tests, model calls or production changes were run while preparing this plan. Implementation approval explicitly covers adding and running the following scoped tests.

  • Configuration: scope validation, backwards-compatible omission, disabled maintenance with missing keys/profile, arbitrary custom model IDs and exact provider-reported model validation.
  • Scheduler: first interval, no overlap, cancellation/shutdown, one dispatch per tick and no restart burst. Use controllable timing rather than long sleeps.
  • Selector: 32 projects with maximum registered sources, complete selected-card evidence, later-card coverage, oversize and evidence-free skips, unchanged sources across restart, source/model change and no model-derived feedback loop.
  • Isolation: a Qdrant fake that fails every request; catalog_only must still complete its run with zero requests. facts_and_catalog preserves existing sweep and manual grouping semantics.
  • Publication: selected subset only, identity/provenance preservation, unknown or cross-project citations, concurrent registration, stale hash, missing sources, cancellation and interrupted state/proposal saves.
  • Adapters and CLI: local fake endpoints exercising both supported protocols and custom model strings; malformed JSON, wrong returned model, timeout and quota outcomes; status emits no private content.
  • Planned command: go test -race ./internal/aipolicy ./internal/aimaintenance ./internal/contextcatalog ./internal/memory ./cmd/ai-maintenance. Build ./cmd/server and ./cmd/ai-maintenance. Map failures to the changed path rather than running unrelated suites.

Subsequent live acceptance: inspect selected source payloads, choose the user's runtime model, approve a bounded independent model-quality pilot, inspect the concrete production config/image diff, then enable catalog-only review before considering evidence_bounded publication. A valid JSON proposal or healthy container alone is not evidence that project boundaries improved.

7. Risks and recovery

The model can create inaccurate ownership boundaries despite valid citations; keep uncertainty explicit and review as default. Catalog changes can invalidate stored recommendations. Shared budget exhaustion skips maintenance and never blocks ordinary writes. Denied cards, missing declarations and unsupported local model schemas must remain observable. Full disk, corrupt state or failed publication preserve the active catalog and baseline service.

Recovery is enabled=false with the normal approved restart, retaining private proposals and snapshots. Restore a reviewed equivalent catalog generation with the current parent hash rather than overwriting a concurrently changed pointer. Preserve original client evidence and declared summaries so generated wording remains reversible. Config fields added by this stage must be removed before rolling back to a strict older binary. No fact grouping rollback is needed because this stage never changes grouping.
