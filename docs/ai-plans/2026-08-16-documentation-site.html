GitHub Issue #32: public documentation site

Prepared 2026-08-16 for Dzarlax-AI/personal_memory. Scope: Starlight documentation, GitHub Pages publishing, content migration, and release-quality documentation checks.

1. Summary

Create a standalone public documentation site inside this repository under website/. Use Starlight to provide structured navigation, local search, responsive rendering, and static output. Publish through GitHub Pages. Keep the README as a concise repository landing page and keep internal AI plans outside the published site.

The initial site documents the current release plus explicit compatibility and upgrade guidance. Multi-version documentation, a custom domain, analytics, and interactive production-connected features are deferred.

2. Current behavior

  • The README contains onboarding, tool reference, configuration, architecture, security, migration, maintenance, and operator procedures in one large page.
  • Authoritative long-form documents exist under docs/, but there is no unified navigation, search, static-site build, or documentation deployment.
  • The only GitHub Actions workflow builds and publishes the service image; documentation has no independent validation or publishing path.
  • Issue #32 requires installation, upgrade, rollback, compatibility, integration-bundle, environment, maintenance, release, and limitation documentation plus clean-install and upgrade rehearsals.

3. Desired behavior and assumptions

  • A reader can reach every issue #32 acceptance topic through task-oriented navigation and local search.
  • The site builds to static files and requires no runtime server, database, credentials, Qdrant, TEI, or production deployment.
  • GitHub Pages is the first hosting target and repository-path hosting works before any custom domain is configured.
  • Starlight and Astro versions are exact or lockfile-pinned. The project uses a committed package lock and reproducible CI installation.
  • Public documentation is English and contains only public concepts, repository facts, and safe placeholders.
  • Existing Markdown is migrated to one canonical public location. The implementation must not leave duplicate, independently editable copies.
  • The current release is the only active documentation line. Compatibility tables and upgrade guides communicate version boundaries without a version selector.

5. Implementation steps

  1. Scaffold the smallest supported Starlight project under website/, pin dependencies, configure the repository Pages base path, and verify an empty production build.
  2. Define navigation for Getting Started, Upgrade and Rollback, Lifecycle, Integration Bundle, Operations, Maintenance, Reference, Architecture/Security, and Limitations.
  3. Inventory README and existing docs sections against issue #32. Assign each topic one canonical destination and identify missing content before moving files.
  4. Migrate existing authoritative documents, repair internal anchors and repository links, and add concise new pages for missing acceptance topics.
  5. Derive command, environment-variable, default, and deprecation reference material from the current source/configuration. Do not invent compatibility claims.
  6. Shorten the README while retaining product identity, minimal local start, development entry point, and prominent documentation links.
  7. Add a GitHub Pages workflow that performs a locked install and production build, uploads only the generated site artifact, and deploys only from the default branch.
  8. Run automated checks, content/safety audit, clean-install rehearsal, and non-production upgrade/rollback rehearsal. Update this plan with evidence.

6. Test and validation plan

Automated

  • Locked dependency install from a clean package state.
  • Starlight/Astro production build using the same command as CI.
  • Internal-link and moved-document reference scan across README, workflows, source comments, and Markdown.
  • Repository secret/path scan focused on public site output and source content.
  • make test to ensure documentation moves do not break repository checks or embedded evidence paths.
  • Inspect the generated output for correct repository base-path asset and navigation URLs.

Content acceptance

  • Installation from prerequisites through authenticated health/use verification.
  • Upgrade with snapshot, immutable image reference, compatibility check, post-upgrade verification, and rollback.
  • Lifecycle migration with dry-run, snapshot, apply, verification, resume/failure handling, and compare-before-restore rollback.
  • Integration bundle install, update, verify, rollback/removal, supported clients, and official UI/admin steps where required.
  • All environment variables, defaults, feature gates, deprecations, and unsafe development escape hatches.
  • Maintenance analyze/quarantine/restore/purge and deprecated forget_old semantics, including stopped-writer and snapshot/archive safety requirements.
  • Release checklist, operational commands, compatibility matrix, known limitations, and unsupported cases.

7. Manual QA and rehearsals

  • Navigate the built site on desktop and a narrow mobile viewport; verify sidebar, search, heading anchors, code blocks, and dark mode.
  • Open the deployed Pages URL without authentication and verify assets, direct deep links, refresh behavior, and canonical links.
  • Follow the public clean-install guide in an isolated temporary environment with placeholders and notifications/invites irrelevant or disabled; record any missing prerequisite or ambiguous step.
  • Rehearse the upgrade and rollback sequence without production mutation: validate commands, expected evidence, snapshot/image pin requirements, and stop conditions against current binaries and compose examples.
  • Confirm destructive maintenance commands are visually distinct, explicit, and impossible to mistake for routine upgrade steps.
  • Verify no published page contains a real API key, personal domain, private IP, absolute workstation path, or production-only identifier.

8. Risks and mitigations

  • Documentation drift: keep a single canonical copy, derive reference tables from code during review, and make the docs build a required PR check.
  • Broken historical links: scan the full repository, preserve practical redirect/index pages when needed, and update workflow/source references in the same change.
  • Pages base-path errors: test generated URLs and a deployed deep link before completion.
  • Dependency overhead: isolate Node dependencies under website/, commit the lockfile, avoid custom plugins unless required, and keep Go CI independent.
  • Unsafe operator guidance: preserve explicit confirmation, snapshot, stopped-writer, archive, and ambiguous-outcome constraints from authoritative source docs.
  • Premature versioning: use compatibility and upgrade pages now; require a new design decision before duplicating version trees.

9. Rollback plan

  1. If the site build or Pages deployment is unreliable, disable/revert the docs workflow while keeping the README usable.
  2. If content migration breaks consumers, restore the old Markdown paths or add small compatibility pages, then repair references before redeploying.
  3. Revert the documentation-only pull request if necessary. No service image, database, memory collection, or production configuration rollback is required.

10. Open questions and deferred scope

  • The final GitHub Pages URL depends on repository Pages settings; custom domain configuration is explicitly deferred.
  • Brand assets should use existing project artwork if available; otherwise the default Starlight presentation is sufficient for the first release.
  • Version selection, localization, analytics, external search, and interactive production tools are not part of issue #32.
