Automatic project access for optional AI

Revision 1 · Implemented locally · Production activation pending · 11 October 2026

Goal and inspected behavior

A fresh installation must support automatic project registration and optional AI without editing a tag list for every new project. Today ensure_project creates owner-scoped declared catalog entries independently of inference. Egress.Allows requires explicitly listed namespaces and tags. catalogWithReason rejects the entire eligible catalog when one card is forbidden. Configuration is loaded at startup. Empty lists permit no inference.

Evidence inspected: internal/aipolicy/config.go; internal/memory/project_registration.go; internal/contextcatalog/registration.go and catalog.go; internal/memory/ai_runtime.go, ai_write.go and ai_read.go. The clean merged shadow-timeout worktree is the implementation baseline; the primary checkout has unrelated changes.

Proposed policy contract

Add an optional egress.project_policy enum: explicit (default, preserving existing behavior) or registered. Add denied_project_tags, with denial taking precedence over every grant. Unknown policy values fail configuration validation. Namespace authorization remains explicit. Choosing registered is a one-time operator authorization for current and future eligible project descriptions within allowed namespaces and the current server owner.

{
  "egress": {
    "project_policy": "registered",
    "allowed_namespaces": ["projects"],
    "allowed_project_tags": [],
    "denied_project_tags": [],
    "unassigned_namespaces": ["projects"]
  }
}

These fields are implemented in the reviewed branch. The effective permission set is derived from the active catalog at request time; ensure_project never edits the private operator configuration. Automatic eligibility requires a valid persisted project identity, matching nonempty owner and eligible declared/approved status. Draft, unresolved, foreign-owner and identity-free legacy cards receive no automatic grant. Explicit grants remain available for existing manual cards. No wildcard namespace grant is introduced.

Separate checks for fact payload scope, optional origin and each catalog card. Existing handling of ordinary explicit tags remains conservative: an unrecognized tag does not gain permission merely because registered mode is enabled. Identity matching and permission decisions must not depend on a model prediction. Registration input and descriptions remain untrusted data.

Fresh-install user flow

  1. The server starts with maintenance, write and read AI disabled. Ordinary memory works with an empty catalog.
  2. The operator chooses a provider and enables registered-project access for projects once. Setup explains that current and future eligible project descriptions may be transmitted. Per-request client opt-in remains required for write inference.
  3. The MCP client reads bounded local project context and calls ensure_project. A successful created/existing result supplies the stable identity. No Git repository is required when the client persists a stable key and the user declares the project.
  4. A subsequent opted-in write sees the new active catalog entry immediately, without a config rewrite or restart. Registration itself dispatches no inference.
  5. Life facts use personal and need no project card. They retain baseline behavior unless a separate namespace policy explicitly authorizes their AI processing. Missing project evidence can result in insufficient_context; no miscellaneous project is fabricated.

Document this flow in the existing optional-AI guide and relevant installation/config examples. Do not claim an interactive setup toggle exists unless an actual inspected setup command is changed.

Catalog projection and exclusions

Registered mode builds the provider catalog from permitted cards only. A denied unrelated card cannot stop an otherwise permitted call. Explicit mode retains its existing all-catalog rejection behavior for compatibility. A forbidden fact, forbidden origin or forbidden read candidate still rejects the entire affected request; candidate filtering must not silently change retrieval behavior.

Card projection continues stripping evidence excerpts, evidence references, project IDs/keys, owner and declared-summary duplicates. AI sees the approved projection fields, including descriptions/examples. If the permitted catalog is empty, record a safe unavailable outcome and use the deterministic baseline. Partial visibility allows abstention; it does not justify routing to the closest visible project.

Bind inference validation to the exact permitted candidate set and catalog generation used for that call. Recheck the current generation and relevant policy before applying any synchronous result; a removed/denied project cannot become a grouping target. Shadow remains advisory. Project maintenance cannot change operator grants or remove denials.

Verification and acceptance

Acceptance checks below are implemented in isolated tests. Run focused Go tests for aipolicy, contextcatalog and memory, then race checks on the touched runtime paths.

  • Missing project_policy retains explicit semantics byte-for-byte where output compatibility matters; empty legacy allowlist still makes no provider call.
  • Fresh isolated empty catalog: register first and second projects, then opted-in writes reach an injected provider with both permitted descriptions without restarting.
  • AI off or request opt-in absent: registration works, provider calls remain zero. Ordinary life facts need no registration.
  • Foreign owner, invalid identity, draft/unresolved, identity-free legacy cards and unknown tag never gain automatic access. Explicit legacy grants still work.
  • Denied card absent from projected payload; denied fact/origin/read candidate blocks the affected request. Denial overrides explicit and automatic grants.
  • Private evidence/identity never crosses the injected provider boundary. A provider response naming an excluded project is rejected.
  • Concurrent registration, removal or policy replacement cannot apply a stale synchronous assignment; generation and allowed-set validation are exercised.
  • All cards excluded and ambiguous facts preserve baseline and expose a fixed reason/abstention; no closest-project fallback.

A production smoke check is a later concrete step using a true fact, bounded request opt-in and confirmed provider scope. Passing injected-provider tests does not prove external model quality.

Risks, recovery and scope boundary

Registered mode intentionally authorizes future descriptions. A client can register an inaccurate description, so identity/owner checks provide access boundaries, not factual validation or secret detection. The setup text must explain the scope. Single-owner server authorization remains the current boundary; this work does not introduce tenant isolation.

Rollback restores explicit policy and the previous config after preserving unrelated settings. Optional AI can be disabled without losing registered projects or stored facts. No database migration, catalog rewrite, provider switch, maintenance enablement or production rollout is included in this revision.
