GitHub Issue #31: lifecycle provenance и history в Viz

План подготовлен 2026-08-16 для Dzarlax-AI/personal_memory. Scope: read-only lifecycle inspection в существующем embedded dashboard.

1. Краткое резюме

Сделать lifecycle-состояние, provenance и связи supersession понятными из защищённого Viz UI. Реализация добавит компактные индикаторы и совместимые фильтры, privacy-safe detail DTO и отдельную ограниченную цепочку истории. Изменение не будет редактировать lifecycle, автоматически решать конфликты или выполнять maintenance-действия.

Рекомендуемый продуктовый фокус: начать с Graph results/detail panel, потому что это уже единственное место, где пользователь выбирает конкретный факт и получает отдельный detail response. Lifecycle badges также появятся в существующих списках, где факт уже показывается.

2. Текущее поведение

  • internal/memory/lifecycle нормализует current, historical, superseded и disputed, legacy-current, canonical, provenance, verification и relationship IDs.
  • GET /viz/api/facts, graph и duplicates уже включают нормализованный lifecycle.View в compact summary, но frontend почти нигде его не визуализирует.
  • GET /viz/api/facts/{id} поддерживает numeric legacy ID и string ID, скрывает quarantined records, но возвращает полный raw Qdrant payload выбранного факта.
  • Graph имеет namespace/tag/text filters, keyboard-доступный results list и отдельную detail panel с tag editor.
  • Нет bounded traversal по supersedes/superseded_by, нет lifecycle/authority filters, нет UI для missing links, cycles или truncated history.
  • Viz остаётся за существующей связкой Traefik Authentik ForwardAuth + application-verified proxy secret; route-level auth в handler не добавляется.

3. Желаемое поведение и API-контракт

Compact lifecycle presentation

  • Каждый показанный факт получает текстовый lifecycle badge; цвет не является единственным способом различения.
  • Дополнительные authority signals показываются явно: canonical, verified, legacy, provenance source и invalid metadata.
  • Provenance не называется trust score: source и canonical/verified остаются отдельными сигналами.

Privacy-safe detail

  • GET /viz/api/facts/{id} перестаёт возвращать unrestricted payload. DTO содержит approved summary, updated_at, last_recalled_at, normalized lifecycle и только безопасные detail fields.
  • List summary не возвращает provenance reference. Detail может вернуть reference только после отказа от absolute filesystem paths, UNC/file URIs и oversized values; иначе возвращает reference_redacted=true.
  • Tag editor продолжает работать через существующий explicit PATCH и не требует raw payload.

Bounded history endpoint

  • Добавить GET /viz/api/facts/{id}/history с детерминированным BFS по обеим relationship-сторонам.
  • Жёстко ограничить число fetched/returned nodes и queued relationship IDs; рекомендуемый initial bound — 32 узла, оформленный константой и покрытый тестами.
  • Ответ содержит privacy-safe nodes, typed links и состояния resolved, missing, unavailable, cycle; отдельный truncated сообщает о сработавшем bound.
  • Quarantined/malformed-maintenance records не раскрываются через history. Invalid lifecycle metadata показывается как invalid node, но не используется для дальнейшего traversal.

Совместимые фильтры

  • Расширить Graph закрытыми query parameters и controls: lifecycle state и authority signal (canonical, verified, legacy, has-provenance).
  • Фильтры работают одновременно с namespace, tag, primary tag и text state и учитываются до max_nodes результата.
  • Неизвестные или повторённые closed-enum параметры возвращают 400, а не молча игнорируются.

5. Этапы реализации

  1. Зафиксировать privacy-safe Viz DTO отдельно от storage-facing lifecycle.View; добавить provenance redaction и timestamp fallbacks без raw payload.
  2. Добавить закрытый parsing lifecycle/authority filters и применить его в bounded graph scan вместе с существующими фильтрами.
  3. Реализовать history resolver с sorted relationships, visited set, cycle/missing/unavailable edges, strict fetch/node bounds и request context cancellation.
  4. Добавить history route и handler-level maintenance/privacy enforcement.
  5. Добавить reusable frontend presentation helpers и lifecycle badges в существующие fact summaries.
  6. Расширить Graph controls и сохраняемый graphFilter, включая reset и server request parameters.
  7. Переделать detail panel на curated lifecycle/provenance/timestamps и lazy history view; сохранить tag editing, retry, stale-request protection, Escape и focus return.
  8. Добавить automated tests, выполнить manual responsive/keyboard/privacy QA и обновить этот план фактическими результатами.

Обязательные test cases

  • canonical, verified, provenance-present filters вместе с namespace/tag;
  • numeric legacy и UUID point IDs;

8. Риски и edge cases

  • N+1 traversal: exact Get нужен для каждого relationship ID. Strict node/fetch bounds, deterministic BFS и cancellation ограничивают стоимость.
  • Privacy regression: нынешний detail возвращает raw payload. Новый allowlist DTO и negative JSON assertions обязательны; provenance reference проходит отдельную redaction.
  • Broken relationship metadata: missing, cycles и malformed states должны быть данными для инспекции, а не panic или бесконечным traversal.
  • Filter semantics: provenance — не authority score. UI использует только явные signals и не делает выводов о truth из similarity.
  • Large datasets: lifecycle filters, которые нельзя безопасно push-down в Qdrant из-за legacy/malformed cases, остаются частью bounded local scan и могут вернуть 422 с просьбой сузить фильтры.
  • Existing payload inspection: удаление raw payload из detail является намеренным privacy hardening и изменяет внутренний Viz API. Перед реализацией это изменение входит в approval данного плана.

9. Rollback и ограничения

Rollback — развернуть предыдущий immutable application image. Изменение read-only и не меняет Qdrant payloads, schema или lifecycle relationships, поэтому data restore и migration rollback не нужны. Tag PATCH остаётся существующим независимым write path.

Не входят в scope: lifecycle editing, merge/delete/truth adjudication, maintenance mutations, graph-based automatic contradiction detection, отдельный auth layer, новый frontend framework и публичная release documentation из issue #32.

10. Предположения и открытые вопросы

  • Рекомендация: history размещается внутри существующей Graph detail panel, а не создаёт новый top-level tab.
  • Рекомендация: raw payload удаляется из detail response; approved fields и payload-key diagnostics при необходимости остаются явно перечисленными.
  • Рекомендация: 32 resolved nodes — первоначальный hard bound. Это operator inspection, не полноценный graph export.
  • Если во время реализации выяснится, что Qdrant exact Get latency делает 32 последовательных запроса неприемлемыми, отдельный batch-get client method допустим только как scoped internal optimization с тем же response bound.
  • Полноценная screen-reader сессия и production Authentik check зависят от доступной среды; пропущенные проверки будут явно записаны в этот файл после реализации.
