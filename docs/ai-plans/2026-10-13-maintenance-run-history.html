Durable maintenance run history

Revision 1 · Draft · Implementation approval pending

Goal and scope

Persist every maintenance pass, including errors and skipped passes, with verifiable references to saved drafts. History survives process restarts and container replacement when the existing state volume is retained. Production remains catalog_only, registered admission, gpt-6-luna, review publication. No fact changes or automatic catalog publication.

This revision covers implementation, isolated tests and documentation. Commit, PR, merge, deployment and live model calls require their corresponding authorization. No new provider calls are needed for the local checks.

Observed baseline

  • Worker.Start invokes RunOnce on each interval and discards its returned error. Both workers overwrite their latest state; this is not a complete history.
  • Catalog outcomes include backoff, no eligible cards, unavailable evidence, no changes, proposal creation and failure. The current failure mapping merges provider and validation failures.
  • Validated proposals are private, content-addressed proposal files, retained until explicitly archived. The current limit of 100 proposal files stops further proposals; it does not delete them.
  • Private state writes sync a temporary file, rename it and sync the directory. A new history store must also prohibit replacement of existing events.

Persistence contract

  1. Use a new private directory under StateDir, maintenance-runs. Each invocation receives a random run ID and an immutable started record, durably written before dispatch. Persist independent immutable events for provider attempts, saved drafts and completion. All records carry a schema version, run ID, session ID and ordered sequence; files are 0600 and directories 0700.
  2. Record UTC timestamps, elapsed time, scope, admission policy, publication mode, protocol/model, catalog generation when available, selected/completed/skipped counts, provider attempt count and available usage. Do not invent missing usage or elapsed values after interruption.
  3. Every enabled RunOnce invocation is represented, including manual calls, scheduler ticks, backoff, no_changes, no_eligible_cards, missing evidence, budget denial, overlapping invocation, cancellation and partial failure. Disabled maintenance does not generate artificial scheduled runs.
  4. Saved-draft events contain the exact relative proposal reference, SHA-256 and created/reused distinction. Emit the event at the actual save/reuse point; never infer this run's drafts from LatestProposal. Multiple drafts and a later failure remain visible together.
  5. Persist terminal outcomes as succeeded, skipped, failed or interrupted, with separate finite reason codes. Capture typed provider failures where available: timeout, canceled, provider_auth, provider_rate_limit, provider_http, provider_transport, invalid_request and invalid_response. Add catalog, source-change, budget, state, capacity and overlap reasons. Unexpected errors map to a fixed unknown_failure; raw errors and provider bodies are never journaled.
  6. On restart, unfinished runs from earlier sessions become interrupted without repeating inference. Graceful shutdown attempts bounded terminal persistence. A started record remains discoverable if terminal persistence fails. Read-only inspection must not relabel a currently active run as interrupted.
  7. Fail before inference if the durable started record cannot be saved. A failure to persist a later event stops further provider dispatch and emits a fixed, content-free operational warning. Reconcile saved proposal references where provable after restart; do not manufacture success. Filesystem failure can prevent recording the failure itself, so the unfinished record and warning are the evidence.
  8. No automatic pruning, overwriting, history reset or deletion. Preserve legacy state and proposal files. Pre-upgrade runs cannot be reconstructed fully; expose the history start boundary rather than fabricating historical outcomes. Existing drafts may be listed as legacy artifacts, clearly separate from new runs.

Private journal metadata is operator state, not analytics telemetry. Do not duplicate assertions, README/AGENTS excerpts, credentials, raw responses, prompts or hidden reasoning. Proposal content remains in its existing private artifact.

Read-only inspection

Add ai-maintenance history --config FILE --limit N and an exact --run-id option, returning structured JSON with run outcomes, reasons and draft references. Bound each listing and provide a stable continuation cursor for older entries. Retain earlier records when the limit is reached. Report missing or corrupt records explicitly, and missing/archived drafts as such; never silently omit them.

Extend status with the latest run ID and history availability. CLI references resolve locally within the configured state directory; no public URLs, dashboard exposure or MCP API changes in this revision. The current image does not bundle ai-maintenance; document the existing operator build/run workflow rather than assuming it is installed.

Risks, recovery and limits

History grows indefinitely by design. At six-hour intervals this creates four scheduled run starts per day, plus any explicit manual invocations. Use bounded records and paginated reads; disk exhaustion stops new inference. Backups must include the state volume and proposals. No implementation can preserve files after volume deletion or guarantee successful writes on failed storage.

A hard kill between provider completion and local persistence can leave an interrupted run with unknown provider outcome. Record that uncertainty; do not resend automatically. Cross-process recovery must distinguish active writers; use a process/session lock for the journal's shared root rather than assuming a second worker is a restart.

Rollback the binary with maintenance disabled before returning to a version that does not journal runs. Retain the new history directory and proposals unchanged; the old binary ignores them. No catalog or fact rollback is needed because this work does not publish or mutate either.

No blocking product questions remain. Exact internal event naming is an implementation choice within this contract. Broader UI, automatic archiving and backup transport changes are separate work.
