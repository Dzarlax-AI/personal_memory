Automatic catalog publication and rollback

Revision 1 · Approved; implementation in progress · 14 October 2026

1. Goal and boundaries

Let the configured maintenance model publish valid project-description updates automatically, without a mandatory human assessment. Preserve every description generation and let the operator inspect and restore a project's earlier version from AI Review. Production uses gpt-6-luna; users can configure another supported generative model. Maintenance remains optional and disabled by default for new installations; review remains the default publication policy.

This change covers catalog descriptions only. It never changes fact text, tags, namespaces, lifecycle or grouping. AI read/write providers and their enablement remain independent. Registered current and future projects require no static allowlist. User-requested activation changes this deployment to catalog_only + registered + evidence_bounded after release verification; it does not switch on fact maintenance.

Fix the two known proposal-quality issues as part of this work. Browser saving was already repaired and deployed through PR #77; retain its sign-in recovery and optimistic assessment revisions.

4. Automatic publication and durable version contract

  • Allow registered + evidence_bounded only with catalog_only and manual grouping. review keeps producing drafts without publication. All defaults remain unchanged. Human assessment is optional observation and never a prerequisite for valid automatic description publication.
  • Reuse the existing source/identity checks, checksum-bound proposals, source projections and compare-before-publish generation guard. Reject malformed responses, unresolved proposals, missing evidence, unavailable references, revoked admission, stale sources, conflicting generations or held projects. These cases remain retained proposals with a finite reason code.
  • Model-editable fields are summary, aliases, owned_components, boundaries, uses, shared_with, positive_examples, negative_examples and validated evidence references. Namespace, project ID/key, owner, tag, name, original declaration, original client evidence, registration identity and operator restrictions are preserved. Automatic output is marked model_derived and automatically published, never human-approved.
  • Add a durable catalog-change journal under the catalog directory. Every new catalog mutation, including registration, manual publication, maintenance and restore, records operation ID, kind, time, previous/new snapshot hashes, changed project IDs and entry hashes. Maintenance entries also link the existing run, proposal checksum, configured model and rule identity. Unknown legacy actor metadata stays unknown.
  • Keep the existing active-pointer format and snapshot checksums compatible. Under the same publication lock, persist an immutable intent and required original context before advancing active.json, then persist an applied receipt. If durable history cannot be written, publication does not proceed. Reconcile interrupted intents on startup from actual immutable generations; unresolved/ambiguous journal state blocks further automatic publication rather than fabricating success.
  • All prior snapshots remain readable. Populate a legacy history view from available snapshot parents and comparisons without inventing model names, run links or approval events. Missing/corrupt history is shown explicitly. Retain all snapshots and receipts in this phase; no destructive history pruning.
  • No-op descriptions produce no new description version. A failed or skipped run remains in maintenance history. A multi-card publication is one guarded catalog generation with separately attributable card changes; held cards are omitted before model selection, rather than forcing a review gate on unrelated projects.

Citation validity and typed constraints do not prove every natural-language claim correct. The user is choosing automatic description publication with visible history and recovery; this plan does not re-label the pilot as a guarantee of model correctness.

5. Restore and publication holds

Restore one card, not an old whole-catalog pointer. Copy the selected historical description fields into the current catalog as a new generation. Preserve all other entries and later project registrations. Verify the historical snapshot and entry hash, current project identity, original-source identity and exact expected active/current-entry hashes. A changed source, missing version or identity mismatch yields a conflict or unavailable result; there is no force overwrite.

Before a restore can change active.json, persist a publication hold for that project under the same catalog lock. This prevents Luna immediately reapplying the discarded description. A crash may leave a hold without a completed restore; the UI reports that state and the operation receipt remains recoverable. Never report restoration until the target generation and durable receipt are verified. Other projects continue automatically.

The hold is optional operational state, keyed by returned stable project identity, and cannot be changed by the model. The operator can explicitly resume automatic publication after inspecting the version and hold state. Keep a durable hold revision and record resume actions. Do not initialize project-specific holds or historical restrictions during this release; no project names are hardcoded into runtime logic.

Use existing proxy-secret authentication and exact configured Origin for writes, bounded JSON bodies, unknown-field rejection, no-store responses, no-follow private storage, fsync and the shared catalog lock. Do not add public endpoints or weaken authentication. Preserve the repaired browser sign-in flow and absence of automatic mutation retries.

6. AI Review workflow

Keep the existing tab and assessments. Add project version history and clearly separate proposed, automatically published, manually restored, rejected/unreviewed and unavailable states. Lack of a human assessment must not make an automatically published version appear unpublished. Published versions remain linked to their producing run and immutable proposal when such provenance exists.

  • Storage tests: intent before pointer advancement; cancellation/disk failure at each boundary; restart after commit but before receipt; checksum corruption; concurrent worker/registration/restore; exact retry; mismatched operation payload; unchanged unrelated cards and future registrations; no mutation when durable journal is unavailable.
  • Automatic mode tests: off/review defaults, registered future-project admission, evidence_bounded eligibility, deny/hold/historical restrictions, unresolved/missing evidence, changed client source, model/rule/policy changes, no-op versions, and no replay of old review proposals after enablement.
  • Quality checks: source-grounded Calendar Sync historical-only, Bridge provider/consumer direction and optional upstreams, external service versus local project ambiguity, and explicitly affirmed shared artifacts. Use isolated fixtures first, then one bounded real catalog-only run with the configured model. No facts enter the maintenance payload.
  • Browser QA: versions from a run and from a project, source/current/history diff, restore preview/confirmation, stale preview 409, lost-response operation lookup, hold visibility and explicit resume, auth expiry recovery, reload persistence, unavailable/corrupt legacy snapshots, narrow viewport and readable English UI.
  • Before activation back up context-catalog and ai-state, including source projections, proposals, assessments, snapshots, journal and holds; record current active hash and stable fact payload checksum. Deploy only the reviewed immutable application image. First verify the UI and protected APIs in review, then activate the requested automatic policy and record the first bounded publication with old/new versions.
  • Validate a real rollback after that bounded publication on the selected description only, keeping the temporary publication hold until explicitly resumed within the approved acceptance sequence. Confirm other cards, registration identities and all fact payloads remain unchanged. This acceptance intentionally creates catalog versions; it is not a read-only test.
  • Recovery: set publication back to review to stop future automatic edits. Restore selected description fields using the new UI and hold semantics; preserve every prior generation. Application/config rollback is separate from description rollback; never replace the whole active catalog with an old generation or delete saved history. Keep source projections and compatible pointer format usable by the prior release.

Risk: generated descriptions can affect Decisions/Jev recommendations even though facts do not change. History makes changes attributable and reversible; it does not prevent every semantic error. Missing evidence remains a retained draft. Retention is unlimited in this phase, so backups/storage growth are observable operating concerns, not silent pruning.
