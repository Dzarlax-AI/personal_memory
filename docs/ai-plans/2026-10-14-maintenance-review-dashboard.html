Maintenance review dashboard

Revision 1 · Implemented locally · Release pending · 14 October 2026

1. Goal and boundaries

Add an English AI Review tab to the existing protected Memory Dashboard so the operator can inspect periodic catalog maintenance and record review outcomes during a rolling two-week observation window. Reuse durable run history and saved proposals. The UI is model-neutral and displays the actual recorded model; gpt-6-luna is the current maintenance choice.

Included: run list, failures and safe reasons, verified proposal detail, field comparisons, evidence excerpts, durable human verdicts and observation totals. Excluded: catalog publication, proposal editing, fact changes, model calls, scheduler/configuration changes and automatic enablement. A human verdict is not publication and never triggers it. Historical projects retain their temporal boundaries.

4. API and persistence contract

  • New GET /viz/api/ai-review/status: availability, actual maintenance mode/model and capabilities. Available history remains readable when scheduling is disabled. An unconfigured installation has a clear empty state.
  • New GET /viz/api/ai-review/runs: limit 1–100, cursor and bounded UTC time window. Backend filtering and pagination preserve eligible records without false totals. The browser initially requests the last 14 days and can inspect older history. Outcome, reason, counts, provider attempts, usage-known flags and draft references remain distinct.
  • New GET /viz/api/ai-review/runs/{run_id}: bounded run/event details.
  • New GET /viz/api/ai-review/runs/{run_id}/drafts/{sha256}: authorize the draft through that run's recorded reference, verify its checksum and validated proposal shape, then produce a safe review DTO. Never accept a filesystem path. No generic artifact/download route.
  • Compare immutable base snapshot, proposal and active snapshot separately. Load source projection only when its recorded entry identity matches; otherwise mark original source unavailable. Do not reconstruct missing historical context from current data. Missing/deleted/corrupt drafts and base snapshots have explicit states.
  • New PUT /viz/api/ai-review/runs/{run_id}/drafts/{sha256}/assessments/{project_id}: verdict acceptable, needs_correction or rejected, bounded reason enum and optional note up to 2048 UTF-8 bytes. Verify project membership and exact draft identity. Request includes expected review revision; stale edits return 409. Initial revision is zero. Reject unknown fields and cap request body at 8 KiB.
  • New internal review store in the existing AI state volume: maintenance-reviews. Append immutable per-project revision records, atomically advance a private head under a dedicated lock, fsync and use mode 0600/0700. A repeated identical request against its expected revision returns the existing result; uncertain save is re-read before retry. New review records bind run ID, draft digest, project ID and compared entry hashes. They never modify proposals, run history or catalog. Changing active catalog marks comparison drift rather than erasing the assessment.
  • Protect all routes with existing Viz authentication. Mutation additionally requires exact same-origin Origin verification and application/json, with no cross-origin allowance. Render untrusted model/source/note text through textContent. Do not expose absolute paths, credentials, raw provider responses, internal dependency manifests or unrelated fact bodies. Private responses use Cache-Control: no-store.

5. Observation and acceptance

Show separately: terminal run outcomes, failed/interrupted/corrupt records, verified proposals, unique project proposal versions, reviewed versions and human verdict distribution. Identical proposals are not counted repeatedly as independent quality evidence. Unreviewed proposals are never successes. Incomplete pagination/scans and unknown usage are visibly incomplete, not zero. No automatic readiness score or automatic promotion to publication.

  • All saved scheduled runs, including failures without drafts, are accessible through paginated history.
  • Review survives refresh and process restart, supports conflict-safe edits, and remains bound to the exact proposal.
  • The operator can trace every proposed relationship to available source evidence and distinguish historical from active dependencies.
  • No review endpoint invokes a provider or changes facts/catalog/configuration.
  • English screen works with direct links, back/forward, keyboard navigation, narrow layouts and refresh. History persists beyond the initial two weeks.

8. Risks, rollback and approval

Private evidence exposure is controlled by authenticated DTOs and safe rendering. Historical proposal inputs may be incomplete; show missing evidence. Concurrency with maintenance is handled by immutable reads and a separate review lock; the UI must not recover or mutate run history. Review growth is preserved without silent expiry; bounded queries and disk errors are explicit. Existing state backups must include maintenance-reviews alongside proposals and run history.

Rollback removes the new routes/tab or reverts the application release while retaining all review files and original history. No destructive cleanup or schema downgrade; future readers validate versions. Publication remains review and existing fact payloads remain unchanged.
