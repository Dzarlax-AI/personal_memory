Client access to write recommendations

Revision 1 · Implemented locally · Production unchanged · 12 October 2026

1. Goal and finite scope

Let an authenticated MCP client retrieve the completed recommendation for its successful shadow write, using the reference returned by store_fact. The result proposes one primary project, lists secondary project recommendations, or explains abstention/failure through validated codes. Reading the result performs no inference.

This increment covers server reference handling, a read-only MCP tool, private journal binding, client usage documentation and isolated protocol checks. It preserves explicit client tags, current provider selection, admission rules, inference budgets and shadow behavior. Experimental hybrid routing, prompt tuning, automatic retagging, maintenance, production configuration and deployment are outside this increment.

Acceptance: an ordinary MCP client can store an eligible synthetic fact and obtain its completed recommendation without SSH. The stored grouping remains unchanged. Off mode, denied admission and duplicate writes produce no new recommendation operation or provider call.

3. Proposed MCP contract

New: get_write_recommendation(operation_ref), registered only when write AI is configured in shadow mode. The existing MCP authentication applies. The deployment's configured memory owner is the access boundary; this change does not introduce separate identities for clients sharing the same credentials.

Input is one exact 32-character lowercase hexadecimal operation reference. Reject malformed inputs before filesystem access. A valid unknown reference and a reference belonging to another owner both return not_found.

FieldContract

statuspending | decided | abstained | failed | outdated | not_found | unavailable.

suggested_primary_tagPresent only for a fresh, validated decided result.
recommended_related_tagsValidated eligible project tags, excluding the primary tag. Empty for every non-decided status.

The response excludes fact text, component context, point IDs, owner identifiers, paths, raw journals and provider payloads. The tool never calls the provider, consumes inference budget, embeds text, increments recall counters or mutates a fact.

store_fact.ai.operation_ref becomes available for successfully journaled eligible shadow writes. The text fallback also includes the reference. Existing response fields and behavior remain compatible. Duplicate and bypassed writes have no new reference.

4. State, freshness and failures

  1. After successful fact persistence, allocate a random reference and atomically save a private version-3 pending journal before enqueueing. Bind it to the deployment owner, exact point ID, a fingerprint of the persisted classification-relevant input/grouping/visibility, runtime instance and catalog generation. Return the reference only after this save succeeds.
  2. The queued worker carries that same reference. Completion, cancellation and queue rejection update the same journal. Secondary suggestions remain recommendations; no shadow tag or payload rewrite is added.
  3. Lookup validates the bounded private journal and exact point ownership, current input fingerprint, ordinary fact visibility and current catalog generation. Changed/deleted/expired/quarantined facts or changed catalogs produce outdated with no suggested tags. Recall counters and recall timestamps do not participate in the input fingerprint. A random server-generated shadow creation marker does; import discards it even if the original creation timestamp is replayed.
  4. A runtime instance ID identifies pending work. Pending journals from an earlier runtime return failed with interrupted; lookup never resumes inference. Completed journals can remain readable across restart if all freshness checks pass.
  5. Journal failure must not turn an already stored fact into a failed write. Return an unavailable AI outcome without a usable reference. A failed terminal journal update leaves pending work bounded by a persisted deadline; once expired, lookup reports failure rather than pending forever.
  6. Read at most 64 KiB, reject symlinks/non-private files and invalid schemas, and use existing secure state-directory checks. Version-2 journals remain operator artifacts and are not exposed by this new API. Backend read failures return unavailable and never disclose raw errors.

Persisted deadline: queue capacity plus the active job bounds waiting to nine times the larger of the configured shadow timeout and the one-second read-job timeout, plus one second of scheduling grace. The shared queue can contain both kinds of jobs. This is an upper bound for status expiry, not a promised completion latency. Freshness checks are observations at lookup time; a later write can invalidate an already returned recommendation. The API grants no authorization to apply it.

7. Risks and recovery

Additional journal I/O occurs after storage and before returning the reference; it must remain bounded and fail open for the fact write. Recommendations can age, so owner/fingerprint/catalog checks are mandatory. Random references are lookup handles, not an alternative to MCP authentication. The existing deployment-owner model does not isolate mutually untrusted holders of shared credentials.

Rollback removes the additive tool and early shadow-reference support from the implementation branch while preserving unrelated changes and facts. Existing operator journals remain private. Disabling write AI is an operator recovery option, but changing production configuration is outside this approval. No Qdrant migration or automatic journal conversion is needed.

Implementation clarifications and limits

The fingerprint is canonicalized through JSON values to handle typed nested Go structs and Qdrant-decoded maps identically. The status-expiry bound uses the larger shared-queue job timeout; this corrects the draft's write-only estimate without changing provider timeout configuration. A random server-generated shadow creation marker is included; import discards it. Recall telemetry is excluded. This addresses the reviewed export/import recreation case; creation time alone is not a unique generation.

The new API uses the existing deployment-owner boundary. Clients sharing credentials are not isolated identities. Freshness is an observation, not an atomic authorization for a future write. Older journals remain private and unconverted. Checks used synthetic providers and isolated backends: they establish protocol/invariant behavior, not provider accuracy or production behavior.
